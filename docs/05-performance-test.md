# 05. 성능 테스트 절차

## 1. 측정 원칙

- 모든 시나리오를 **Track A(공통 레이크)** 와 **Track B(각자 최적)** 에서 각각 측정한다.
- 각 쿼리는 **3회 이상 반복**하고 **중앙값**을 채택한다. 편차가 20%를 넘으면 원인 규명 전까지 채택하지 않는다.
- 캐시 상태(콜드/웜)를 명시하지 않은 측정값은 **무효**로 처리한다.
- 실패(오류·타임아웃·OOM)는 성공 측정에서 제외하지 않고 별도 열에 기록한다.
- 부하 발생기는 엔진 노드와 분리된 별도 노드에서 실행한다.

## 2. 캐시 통제 프로토콜

| 상태 | 정의 | 준비 절차 |
|---|---|---|
| **콜드(Cold)** | 엔진 캐시 · OS 페이지 캐시 모두 비어 있음 | 엔진 재시작 → 데이터 캐시/쿼리 캐시 비활성 → 전 노드 `sync; echo 3 > /proc/sys/vm/drop_caches` |
| **웜(Warm)** | 동일 쿼리 2회 선행 실행 후 | 대상 쿼리 2회 실행 후 3회부터 측정 |

- StarRocks: 데이터 캐시 · 쿼리 캐시 설정을 트랙별로 고정하고 그 값을 기록한다.
- Trino: 파일시스템 캐시 설정을 동일 기준으로 고정한다.
- 콜드/웜을 섞어서 평균하지 않는다. 두 값을 각각 보고한다.

## 3. 성능 시나리오

### P1. 단일 쿼리 지연 (배점 10)

| 항목 | 내용 |
|---|---|
| 쿼리셋 | TPC-H 22개, TPC-DS 99개 |
| 동시성 | 1 (순차 실행) |
| 캐시 | 콜드 1회 + 웜 3회 |
| 대표값 | 웜 실행 시간의 **기하평균** (산술평균은 장시간 쿼리에 지배되므로 사용하지 않음) |
| 부가 기록 | 쿼리별 스캔 바이트, 피크 메모리, CPU 시간, 실패 여부 |

기록 양식: [08-결과 기록 §2](08-result-templates.md#2-p1-단일-쿼리-지연).

### P2. 대시보드 응답 시간 (배점 10의 일부)

| 항목 | 내용 |
|---|---|
| 쿼리셋 | SSB 13개 + 사내 대시보드 대표 쿼리 5~10개 |
| 특성 | 필터 + 집계 위주, 응답 데이터 소량 |
| 목표 | p95 응답 시간 (SLA 임계값과 대조) |
| 캐시 | 웜 |

> 여기서 측정한 p95를 [결격 조건 K2](01-evaluation-criteria.md#4-결격-조건-knock-out)의 SLA와 대조한다.

### P3. 동시성 (배점 10)

| 항목 | 내용 |
|---|---|
| 동시 사용자 | 1 → 5 → 10 → 20 → 50 → 100 (단계별) |
| 지속 시간 | 단계당 10분 (워밍업 2분 제외) |
| 쿼리 혼합 | 대시보드형 70% + 분석형 25% + 대용량 5% |
| 측정 지표 | QPS, p50/p95/p99 지연, 에러율, 큐 대기 시간, 노드 CPU/메모리 |
| 종료 조건 | 에러율 5% 초과 또는 p95가 SLA의 3배 초과 시 해당 단계에서 중단 |

**포화점(saturation point)** — QPS가 더 이상 증가하지 않는 동시 사용자 수 — 를 반드시 기록한다.
이 값이 실시간 BI 관점 권고의 핵심 근거다.

부하 도구: **Apache JMeter JDBC Request** 로 통일한다.

| 엔진 | JDBC 드라이버 | URL 예시 |
|---|---|---|
| Trino | `io.trino:trino-jdbc` | `jdbc:trino://coordinator:8080/iceberg/tpch_sf100` |
| StarRocks | MySQL Connector/J | `jdbc:mysql://fe:9030/tpch_sf100` |

> 도구를 통일하지 않으면 클라이언트 오버헤드 차이가 결과를 오염시킨다. JMeter 테스트 플랜(`.jmx`)을 저장소에 커밋한다.

### P4. 대용량 처리 (배점 5)

| 항목 | 내용 |
|---|---|
| 데이터 | TPC-H SF1000 (또는 가용 최대 규모) |
| 쿼리 | 대용량 셔플 조인(TPC-H Q9, Q21), 전체 스캔 집계 |
| 측정 | 완주 여부, 소요 시간, 스필(spill) 발생량, 피크 메모리 |
| 판정 | 메모리 부족 시 디스크 스필로 완주하는지, 아니면 실패하는지 |

동시 자원 초과 상황에서의 **우아한 저하(graceful degradation)** 여부가 핵심 관찰 포인트다.

### P5. 적재 성능 (배점은 성능/운영성에 분산)

[03-데이터셋 §6](03-dataset.md#6-적재-성능-측정-성능-항목에-반영) 참조.
배치 적재 처리량, 스트리밍 적재 지연, 적재 중 조회 영향(p95 저하율)을 측정한다.

### P6. 자원 효율 (배점 5)

동일 워크로드(P1 웜 전체 1회 완주) 기준으로 비교한다.

| 지표 | 수집 방법 |
|---|---|
| 총 CPU 초 | Prometheus `node_cpu_seconds_total` 구간 적분 |
| 피크 메모리 | 엔진 지표 + node_exporter 최대값 |
| 총 읽은 바이트 | 엔진 쿼리 통계 및 스토리지 지표 |
| 네트워크 전송량 | node_exporter |

> "누가 빠른가"와 "같은 일에 자원을 얼마나 쓰는가"는 다른 질문이다. 후자는 비용 산정의 입력값이 된다.

## 4. 확장성 측정 (확장성 10점)

| 절차 | 내용 |
|---|---|
| 1 | 연산 노드 3대 구성에서 P3 동시성 50 사용자 QPS 측정 (기준값) |
| 2 | 연산 노드 6대로 확장. 확장 소요 시간 및 무중단 여부 기록 |
| 3 | 데이터 재분배 완료까지 대기 (StarRocks tablet 재분배 등). 완료 판정 기준과 소요 시간 기록 |
| 4 | 동일 조건으로 QPS 재측정 |
| 5 | 선형성 계수 = (확장 후 QPS / 확장 전 QPS) / 2 |

확장 중 진행 중인 쿼리의 실패 여부를 함께 기록한다.

## 5. 성능 이상 시 조사 절차

측정값이 예상과 크게 다를 때, 결론을 내기 전에 아래를 순서대로 확인한다.

1. 통계 정보가 최신인가 (`ANALYZE` 누락이 가장 흔한 원인)
2. 파티션 프루닝이 동작하는가 (스캔 바이트로 확인)
3. 조인 전략이 적절한가 (Broadcast/Shuffle 선택 확인)
4. 작은 파일이 과다한가 (파일 수 · 평균 크기 확인)
5. 캐시 상태가 의도대로인가
6. 특정 노드에 스큐가 있는가 (노드별 CPU 편차 확인)
7. GC 또는 스필로 시간이 소모되는가

조사 결과와 조치 내역을 기록하고, **조치 후 재측정한 값을 채점에 사용**한다.
한쪽 엔진만 튜닝하고 다른 쪽은 하지 않는 상황을 만들지 않는다.

## 6. 완료 조건

- [ ] P1~P6 전 시나리오를 Track A · B 모두에서 측정 완료
- [ ] 모든 측정값에 캐시 상태 · 트랙 · 반복 횟수가 기록됨
- [ ] 실패 쿼리 목록과 사유가 정리됨
- [ ] 포화점 및 선형성 계수 산출 완료
- [ ] JMeter 플랜, 쿼리셋, 원시 CSV가 저장소에 커밋됨
