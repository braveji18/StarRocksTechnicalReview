# 06. 운영성 · 장애 복구 테스트 절차

## 1. 설치 · 초기 구성 (배점 4)

| 측정 항목 | 기록 내용 |
|---|---|
| 설치 소요 시간 | 빈 노드 → 첫 쿼리 성공까지 (분) |
| 수동 개입 단계 수 | 자동화 불가하여 사람이 수행한 단계 수 |
| 사전 요구사항 | 런타임 버전, 커널 파라미터, 파일 디스크립터 한도 등 |
| 배포 자동화 | Helm chart / Operator 제공 여부 및 성숙도 |
| 설정 난이도 | 필수 설정 파일 수, 기본값으로 동작 가능 여부 |
| 오류 진단성 | 설정 오류 시 메시지가 원인을 지목하는가 |

설치에 사용한 매니페스트/스크립트를 저장소에 커밋한다.

## 2. 스케일 아웃 / 인 (배점 4)

| 시나리오 | 절차 | 기록 |
|---|---|---|
| O-01 연산 노드 증설 | 3 → 6대 확장 | 소요 시간, 무중단 여부, 데이터 재분배 완료 시간 |
| O-02 연산 노드 축소 | 6 → 3대 축소 | 진행 중 쿼리 보존 여부(graceful shutdown), 데이터 안전성 |
| O-03 제어 노드 증설 | Coordinator / FE 추가 | 지원 여부, 절차 복잡도 |
| O-04 확장 중 서비스 영향 | 확장 작업과 동시에 부하 인가 | p95 지연 변화율, 에러 발생 |

> StarRocks shared-nothing 모드는 노드 증감 시 tablet 재분배가 발생한다. **재분배 완료 판정 기준**
> (예: 관련 지표가 정상 상태로 복귀)을 사전에 정의하고, 완료 시각까지 측정한다.
> Trino는 워커가 상태를 갖지 않아 즉시 활용되지만, 축소 시 진행 중 쿼리 처리 방식을 확인한다.

## 3. 롤링 업그레이드 (배점 2)

| 절차 | 확인 사항 |
|---|---|
| 1 | 현재 버전에서 지속 부하 인가 시작 |
| 2 | 제어 노드부터 순차 업그레이드 |
| 3 | 연산 노드 순차 업그레이드 |
| 4 | 전 과정의 에러율 및 다운타임 측정 |
| 5 | 롤백 절차 존재 여부 및 소요 시간 |

버전 간 호환성(구/신 버전 혼재 허용 여부)을 문서와 실측으로 함께 확인한다.

## 4. 백업 · 복구 (배점 6)

두 엔진은 **백업 대상 자체가 다르다.** 이 비대칭성을 결과표에 명시한다.

| 대상 | Trino | StarRocks |
|---|---|---|
| 데이터 | 엔진이 소유하지 않음 (레이크/원본 시스템의 책임) | 네이티브 테이블 데이터 (엔진 책임) |
| 메타데이터 | 카탈로그 설정 파일 + 외부 메타스토어 | FE 메타데이터 (내부 카탈로그 스키마 포함) |
| 권한/사용자 | 설정 파일 또는 외부 시스템 | 엔진 내부 |

| 시나리오 | 절차 | 기록 |
|---|---|---|
| O-10 전체 백업 | 정의된 백업 대상 전체 백업 수행 | 소요 시간, 백업 크기 |
| O-11 전체 복구 | 신규 클러스터에 복구 | RTO(복구 시간), 데이터 정합성 |
| O-12 부분 복구 | 특정 테이블/스키마만 복구 | 지원 여부, 소요 시간 |
| O-13 시점 복구 | 특정 시점으로 복구 (Iceberg time travel 포함) | RPO, 지원 범위 |
| O-14 메타데이터 손상 복구 | 제어 노드 메타 디렉터리 손상 후 복구 | 복구 가능 여부, 절차 |

복구 후 [03-데이터셋 §5](03-dataset.md#5-적재-검증)의 체크섬 검증을 반드시 재실행한다.

## 5. 장애 주입 시나리오 (안정성 10점)

각 시나리오는 **지속 부하(동시 10 사용자) 인가 상태**에서 수행한다. 무부하 상태의 장애 테스트는 의미가 없다.

| 코드 | 장애 | 주입 방법 | 관찰 항목 |
|---|---|---|---|
| **F1** | 연산 노드 1대 다운 | 프로세스 kill (쿼리 실행 중) | 실행 중 쿼리 실패/재시도 여부, 신규 쿼리 정상 여부, 복구 시간 |
| **F2** | 제어 노드 리더 다운 | 리더 프로세스 kill | 서비스 중단 시간, 자동 승계 여부, 클라이언트 재연결 필요 여부 |
| **F3** | 메타스토어 다운 | HMS/REST 카탈로그 중지 | 기존 조회 지속 가능 여부(캐시), 신규 조회 실패 양상 |
| **F4** | 오브젝트 스토리지 장애 | 네트워크 차단 및 지연 주입(`tc netem`) | 타임아웃 처리, 재시도, 오류 메시지 명확성 |
| **F5** | 디스크 고갈 / 네트워크 분리 | 디스크 채우기, 노드 격리 | 스플릿 브레인 방지, 데이터 정합성 |
| **F6** | 폭주 쿼리 (OOM 유발) | 초대형 카티션 조인 실행 | 해당 쿼리만 실패하는가, 다른 쿼리/클러스터에 영향이 있는가 |

### 5.1 F1 보조 측정 — 내결함성 실행

Trino는 내결함성 실행(fault-tolerant execution) 활성 여부에 따라 F1 결과가 달라진다.
**비활성/활성 두 경우를 각각 측정**하고, 활성 시의 성능 오버헤드(P1 기하평균 증가율)를 함께 기록한다.
성능 손실 없이 얻는 안정성이 아니므로, 트레이드오프를 결과표에 명시한다.

### 5.2 기록 양식

| 항목 | 기록 |
|---|---|
| 장애 감지 시각 / 복구 완료 시각 | |
| 서비스 중단 시간 | |
| 실행 중 쿼리 결과 | 성공 / 자동 재시도 성공 / 실패 |
| 신규 쿼리 영향 | |
| 데이터 유실 여부 | (유실 시 [결격 조건 K3](01-evaluation-criteria.md#4-결격-조건-knock-out) 해당) |
| 수동 개입 필요 여부 | |
| 오류 메시지 품질 | 원인 파악 가능 / 불명확 |

## 6. 모니터링 · 멀티테넌시 (배점 4)

### 6.1 관측성

| 항목 | 확인 내용 |
|---|---|
| 기본 지표 노출 | Prometheus 호환 엔드포인트 제공 여부 |
| 공식 대시보드 | 제공 여부 및 완성도 |
| 쿼리 이력 | 실행 이력 조회, 보존 기간, 검색성 |
| 실행 프로파일 | 단계별 소요 시간·행 수·메모리 확인 가능 여부 |
| 느린 쿼리 추적 | 임계값 기반 자동 기록 |
| 로그 품질 | 오류 원인 추적 가능성 |

> 실무에서 "왜 느린가"를 답할 수 있는지가 핵심이다. Trino는 `EXPLAIN ANALYZE`와 이벤트 리스너,
> StarRocks는 Query Profile을 사용하여 **동일한 느린 쿼리 1건을 실제로 진단**해 보고 그 경험을 기록한다.

### 6.2 멀티테넌시 격리

| 시나리오 | 절차 | 판정 |
|---|---|---|
| O-20 리소스 그룹 정의 | 그룹별 CPU/메모리/동시성 한도 설정 | 설정 가능 여부 |
| O-21 격리 실효성 | 저우선순위 그룹에 폭주 워크로드 인가 | 고우선순위 그룹의 p95 지연 변화율 |
| O-22 쿼리 큐잉 | 한도 초과 시 대기 vs 거부 | 동작 방식 및 제어 가능성 |
| O-23 쿼리 강제 종료 | 실행 중 쿼리 kill | 즉시 종료 여부, 자원 회수 |

O-21에서 **고우선순위 그룹 p95 저하율이 20% 이내**면 격리가 실효성 있다고 판정한다.

## 7. 완료 조건

- [ ] O-01 ~ O-23 전 시나리오 수행 완료
- [ ] F1 ~ F6 장애 주입 완료 (모두 부하 인가 상태에서 수행)
- [ ] 복구 후 데이터 정합성 검증 완료
- [ ] 결격 조건(K3, K4) 해당 여부 판정 완료
- [ ] 장애 주입 스크립트가 저장소에 커밋됨
